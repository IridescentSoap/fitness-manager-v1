# 03 业务规则（实现与测试的权威来源）

## 0. 核心不变量

- 每用户同时只有一个启用中的周循环计划；不同用户互不影响。
- 训练安排（应做什么）、训练记录（实际做什么）、统计结果三者分离；一律使用服务端计算结果。
- 训练后记录：**没有开始训练动作**，只有“打开某日任务 → 勾选（自动保存草稿）→ 手动提交”。
- **已提交记录与历史应执行任务不可因后续计划编辑而消失或被改写。**
- 训练汇总与体重数据默认仅本人可见；共享为明确的、可撤销的独立开关。

## 1. 日期与时区

- 系统业务时区由 `APP_TIMEZONE` 配置，默认 `Asia/Shanghai`；日期 `YYYY-MM-DD`、时间戳 UTC ISO8601（带 `Z`），前端展示转换到业务时区。Windows 电脑系统时区不影响历史日期归属。
- 周一为 1，周日为 7。`from`/`to` 含首含尾，最长 366 天；`to < from` 返回 422。
- “今日”按服务端业务时区确定；计划生效区间和日历计算必须使用同一时区。

## 2. 计划、日期调整与任务生成

### 2.1 固定周计划

- 每用户最多一个 `ACTIVE` 周计划（通过事务锁/唯一部分索引保证）。
- 周计划 `start_date` 起生效，`end_date` 可空（长期）；一周内 weekday 不重复。当天若配置为休息，不生成训练任务。
- 计划编辑对**今天及未来尚未提交的日期**可生效，但**过去日期及已提交任务**的快照不可变；不得通过后来编辑删掉过去应完成任务。

### 2.2 日期覆盖优先级

同一用户同一天至多一条日期调整（`date_overrides`）：

1. `REST`：当天不生成周计划任务和额外任务；已提交历史记录仍保留。过去日期不能用该操作追溯消除应完成任务。
2. `REPLACE`：用指定日期的一组自定义动作任务替代周计划任务。
3. `ADD`：保留周计划任务，另外增加一场自定义任务；当日最多两场由计划产生的任务。
4. 无调整：使用当天周计划任务。若周计划当天无训练，日程显示休息/未安排。

用户还能主动添加 `AD_HOC` 自主训练，此任务独立于周计划/临时计划，不改变计划完成率分母。

### 2.3 “任务快照”冻结机制

- 建立 `schedule_occurrences`：每个应执行的计划训练任务对应一条持久记录（`WEEKLY`/`OVERRIDE`），包含训练日期、来源、显示名称与目标动作 JSON 快照；状态为 `PLANNED` 或 `CANCELLED`（取消只允许未来/当日尚无提交的任务）。
- 周计划新建/启用/编辑、日期覆盖新增/变更时，**事务内**仅重建受影响的今天及未来 `PLANNED` 且未提交任务；过去发生日、已提交/已录入草稿且发生编辑冲突的任务不得悄悄重写：应返回 `409 TASK_HAS_RECORD`，要求用户先明确处理记录。
- 为保证“即使服务关闭数日也不丢历史应做任务”，激活周计划时为有效期未来 365 天预生成任务；每天及服务启动时继续向未来滚动补齐到 365 天，先补齐到当前日期再处理计划变更。每个任务由 `(user_id, workout_date, slot)` 唯一标识，其中 `slot=BASE|EXTRA`；REST/REPLACE 可取消或替代 BASE，ADD 产生 EXTRA。历史不物理删除。长期计划采用向前滚动窗口；未生成的更远期由月历预览动态计算但不纳入正式历史统计。
- 规则补充：当系统长期关机超过 365 天，重启时按**持久化的计划修订历史**补齐缺失日期，不能直接用当前修订推算过去；V1 应保存 `plan_revisions`（生效时间段及内容快照）并按修订历史重建缺口。日期调整也保存生效/修改审计。可通过集成测试验证。
- `schedule_occurrences` 包含 `scheduled_snapshot`、`revision_id`，历史统计只读取已冻结的应执行任务及提交记录，不根据现行计划重新推导旧日期。

## 3. 记录提交规则

- 打开某任务，尚无训练记录时由首次勾选/点击保存草稿创建 `workout_sessions(status=DRAFT)`；同步复制 occurrence 的目标动作快照到 `workout_exercises`，每条动作含结构化 `sets[]`（组序号、次数/重量或时长/距离、组完成状态）。
- 草稿不计入已完成训练、计划完成率/动作完成率分子；已有应执行任务仍计入其分母。
- 可 PATCH 单组完成/数值，或动作级 `completed`（映射为该动作全部组勾选/取消）；重复请求幂等；使用 `version` 乐观锁，冲突返回 409 与最新版本。动作行 `completed` 派生为「全部组已完成」。
- 用户点击**提交**，允许完成 0、部分或全部组；提交后 `status=SUBMITTED`，记录 `submitted_at`，完整结果由服务端按**组**推导：
  - `FULL`: 总组数>0 且完成组数=总组数；
  - `PARTIAL`: 0<完成组数<总组数；
  - `NONE`: 完成组数=0。
- 不允许空动作列表提交；自主训练至少包含 1 个动作，可一次创建多个动作；每项至少 1 组（可空值，提交前可补全）。旧自由文本 `capacity` 仅兼容回显，新写入以 `sets` 为准。
- 已提交记录默认只读；进入“编辑历史”后显式执行 `reopen`（审计）进入 DRAFT，重新提交后统计更新。未重新提交的旧记录暂不在已提交汇总中，历史页面提示“重新编辑中”；需有确认对话。
- `AD_HOC` 训练不对应计划 occurrence；支持任意历史日期，不得伪造计划完成率分子。自主训练也可提交和计入完成次数/实际训练天数。
- 删除已提交记录仅允许本人经过二次确认执行**软删除**，保留审计；计划任务仍留作未完成。

## 4. 历史修改规则

- 计划编辑或动作库重命名都不得更改已生成的 occurrence 和已提交的 session 快照；已提交事实按用户明确编辑流程修改。
- 当日“临时休息”只允许无已提交/草稿的日期覆盖：若有记录先明确操作；过去日期不得修改成 REST/REPLACE 以提升历史完成率。历史错误只能通过记录编辑修正，并写入审计。
- 同一天可有 BASE、EXTRA、多个 AD_HOC。训练**次数**按照已提交且至少一个动作完成的 session 计数；训练**天数**去重日期。

## 5. 统计口径（必须编写自动测试）

选定 `[from,to]`，只含未软删除记录，按用户+日期归属。

- **已完成训练次数** `C_sessions`：`SUBMITTED` 且 `completed_count > 0`（按组计数）的 session 条数（含自主训练）；提交 0 组完成不计“完成”。
- **实际训练天数** `C_days`：满足上述条件的不同 `workout_date` 的个数。
- **应执行计划任务数** `P_due`：日期范围内历史冻结的 schedule_occurrences（`PLANNED`，来源 WEEKLY/OVERRIDE），不含被合法 REST/REPLACE 取消的任务，不含 AD_HOC。当前/未来日程可显示但**历史完成率只统计到统计区间截止日与今天之间较早的日期**，防止把未来计划算未完成。
- **完整完成计划任务数** `P_full`：对应 occurrence 的 `SUBMITTED` 且结果 `FULL`（该 session 计划动作的全部组均完成；追加 `is_extra` 组不计入判定）的 session 数。
- **计划完成率** `100*P_full/P_due`。`P_due=0` 返回 `null`（前端显示“—”），**不是 0% 或 100%**。允许 `PARTIAL` 另行计数，不算完整完成。
- **计划动作完成率** `100*sum(completed sets of associated SUBMITTED plan actions)/sum(target set count of P_due occurrence snapshots)`，无提交的应执行任务分子为 0；仅对 `P_due` 内计划任务计算，**不含自主训练与 is_extra 追加动作**；分母为快照组数（无 `sets` 时回退为动作行数或 `target_sets`）。若 0 返回 null。
- **动作完成频次**：按 `exercise_id` 汇总已提交 session 中动作行 `completed=true`（全部组完成）的数量；若名称变化可统一按 ID 统计，历史详情显示快照名称。
- **休息日**无计划任务，不计应执行数；提前合法临时休息也不计；过去日期事后取消不得改变历史分母。
- 同一日计划任务 2 场，只要都应执行，`P_due +=2`；`C_days`最多加 1。
- **本月/本周**：业务时区自然月/周，默认区间到今天；90天包括今天的最近 90 个日期；自定义区间含首尾。
- **排行榜**：训练次数、实际训练天数降序；计划完成率、计划动作完成率降序；没有可定义分母的用户显示“无数据”且不参与该项名次；并列名次使用 competition ranking (1,1,3)。不计算综合总分。

## 6. 体重统计规则

- 体重单位 kg，输入合法范围 20.0~400.0 kg，最多 2 位小数；不作健康诊断。`recorded_at` 是实际测量时间，`record_date` 为业务日期；允许历史补录且同日多条。
- “日体重”取同日 `recorded_at` 最新的一条，若相同以 id 大者为准。最新体重取全历史测量时间最新且未删除的一条。
- 选定时间范围体重阶段差 `Δ=W_end-W_start`；相对变化 `Δ% = 100*Δ/W_start`（`W_start>0`）；有效日观测少于两天时显示 null；图表缺测日期为 `null`，不能视为 0，也不得绘制虚构测量点。
- 目标体重仅本人展示，值可空；体重下降不自动视为更好，**不建立体重下降排行榜**。

## 7. 隐私与比较规则

- `share_training_stats`、`share_weight_change`、`share_weight_values` 初始全部 `false`。分别控制：
  - 训练汇总：其他用户可见汇总指标（无动作明细、计划细节、草稿）。
  - 体重变化：仅公开所选时间段的变化 kg/%（需至少两个有效日）；**不公开具体体重数值**。
  - 体重原始值：可见具体历史体重日数据与曲线（客观上可推导变化），设置页须明确告知。
- 用户可开启任意单项；即使未开放训练统计，也可单独开放体重变化/数值，但不会出现在训练排行榜。
- 比较页用户选择器按对应指标授权过滤；最多选 5 人，最少 2 人用于横向图；本人始终可看自己的指标，但**本人不因登录自动向其他用户共享数据**。
- 共享撤销立即影响之后所有 API 响应；不缓存授权失效前的私有结果；HTTP 响应 `Cache-Control: no-store`。
- 排行榜仅纳入已开放训练汇总且所选区间有对应有效指标者；按同一区间统计，不比较完整个人训练明细。
- 管理员没有额外读取其他用户体重原值的特权。管理员仅做账户/系统管理。

## 8. 并发与错误

- 训练 checkbox PATCH 与历史修改须检查 session 的 `version`；冲突 `409 VERSION_CONFLICT` 并返回最新版摘要供 UI 刷新，不静默覆盖。
- 同一用户重复请求“创建当日任务/草稿/提交”必须使用唯一约束及幂等处理；遇 SQLite 写锁短暂重试但不能提交两次。
- 不同用户的写操作独立；从用户 A 的资源 URL 猜 ID 查询，返回 404（避免泄露存在性）。
- 不能通过浏览器直接连接 SQLite；API 是唯一数据入口。
